# Careers@Gov Hiring Trends Pipeline

Builds a daily pipeline for one agency: **crawl → analyze (Claude) → dashboard → email**, with all data accumulating in a project folder ("workdir"). The bundled scripts in `scripts/` are complete and tested — run them directly from the skill directory with `--workdir` pointing at the project folder; don't rewrite them. If the user needs behavior the flags don't cover, copy the relevant script into their project and modify the copy.

## The data source (critical — easy to get wrong)

Careers@Gov job data comes from the **Open Government Products public mirror**, refreshed daily:

```
https://raw.githubusercontent.com/opengovsg/careersgovsg-jobs-data/main/data/job-listings.json
```

This is the same data the jobs.careers.gov.sg search UI shows (~2,000+ postings, ~90 agencies). Two traps:

1. **Do NOT use the Workday tenant** `sggovterp.wd102.myworkdayjobs.com` that turns up when probing the site. It looks like the backend but is a separate/legacy system missing most agencies (HTX has zero postings there). The real backend is SAP HRP and not public; the OGP mirror is the sanctioned public copy.
2. **Agency names in the mirror are full names**, not codes: "Home Team Science and Technology Agency (HTX)", "Government Technology Agency" (not "GovTech"/"GVT"), "Monetary Authority of Singapore". The crawler's `--agency` flag is a case-insensitive **substring match** on that field — beware false positives too: the substring "MAS" matches "Te**mas**ek Polytechnic", so prefer a distinctive fragment like "Monetary". When unsure, run:
   ```
   python scripts/careers_gov_crawler.py --list-agencies
   ```
   A zero-match crawl also prints suggested agency names automatically.
3. **Postings with no closing date are open-until-filled and count as active** (GovTech lists ~96% of its jobs this way). The bundled crawler and dashboard already handle this; keep that behavior if modifying them, or agencies like GovTech silently shrink from ~276 postings to ~10.

## Setup workflow for a new agency

1. **Dependencies**: `requests`, `pandas`, `openpyxl`, `anthropic`, `python-dotenv`, `matplotlib`. Install any that are missing.
2. **Workdir**: pick/create the project folder. Create `<workdir>/.env` with `ANTHROPIC_API_KEY` (needed for skill extraction; the crawl works without it). Verify the key with a tiny test call before the big run — users sometimes paste non-Anthropic keys (real ones start `sk-ant-`) or have zero API credits (401 vs a 400 "credit balance too low" respectively).
3. **Find the agency's mirror name** (`--list-agencies` or a test crawl), then first crawl:
   ```
   python scripts/careers_gov_crawler.py --agency "<name fragment>" \
       --output <workdir>/<prefix>_job_postings.xlsx --history-file <workdir>/<prefix>_job_history.csv
   ```
4. **First analysis** — mind the cost: each posting = one Claude call (claude-sonnet-4-5, ~US$0.005 each). Results are cached per Job ID in `<prefix>_skills_cache.json`, so this cost is paid once per posting ever. For a first run on a big agency, offer the user `--limit 10` to sanity-check output before the full spend. Note that if the user set a hard analysis cap, a retry after a transient API error can pick up extra uncached postings — re-pass the same `--limit` on retries to honor the cap strictly.
   ```
   python scripts/skills_analysis.py --history-file ... --cache-file ... \
       --agency-name "<display name>" --output <workdir>/<prefix>_skills_analysis.xlsx
   ```
5. **Dashboard + full run**: the orchestrator does crawl → analyze → dashboard → trend image → email in one command:
   ```
   python scripts/daily_report.py --agency "<name fragment>" --agency-name "<display name>" \
       --prefix <prefix> --workdir <workdir> [--no-email]
   ```
6. **Email** (optional): add to `.env`: `SMTP_USER` (Gmail address), `SMTP_APP_PASSWORD` (from myaccount.google.com/apppasswords — requires 2FA; **must be generated by the SMTP_USER account**, a mismatch gives 535 BadCredentials), `REPORT_EMAIL_TO`. Then run `daily_report.py` without `--no-email` and confirm receipt.
7. **Schedule** (Windows):
   ```
   schtasks /Create /F /SC DAILY /ST 08:00 /TN "<Agency> Daily Hiring Report" \
       /TR "\"<python.exe>\" \"<skill>/scripts/daily_report.py\" --agency \"...\" --agency-name \"...\" --prefix ... --workdir \"...\""
   ```
   Use `sys.executable`'s full path. Warn the user: the task runs under their login, so the PC must be on (not asleep) at the scheduled time.

## What gets produced (all in workdir, prefix = agency shorthand)

| File | Contents |
|---|---|
| `<prefix>_job_history.csv` | Accumulating archive keyed by Job ID with First Seen / Last Seen — postings vanish from the live feed when they close, so this is the source of truth for trends |
| `<prefix>_skills_analysis.xlsx` | 8 sheets: Postings (with Division, Job Level Raw/Band, skills), Skills Detail, Category Trend Monthly + Weekly, Top Skills, Skills by Division, Skills by Level, Headcount Trend |
| `<prefix>_dashboard.html` | Self-contained static dashboard (no JavaScript — see email rules below) |
| `<prefix>_trend.png` | Weekly trend line chart for the email body |
| `<prefix>_daily_report.log` | Append-only run log |

## Analysis design decisions (explain these to the user if asked)

- **Skills taxonomy**: 13 fixed categories (see `SKILL_CATEGORIES` in skills_analysis.py). Claude extracts 3–15 specific skills per posting and assigns each to one category.
- **Job level**: two columns — the raw title wording ("Lead Engineer/Engineer") and a standardized band (Engineer/Officer → Senior/Lead → Principal → Manager → Head → Deputy Director → Director & Above), taking the **higher** band for dual-level titles.
- **Division**: inferred by Claude from title suffixes + JD text (Singapore agencies often encode it, e.g. HTX's "…, Red Team, xCyber"), normalizing variants. Expect some fragmentation; offer a consolidation pass if the user wants cleaner rollups.
- **Weekly trend**: a posting counts toward every week its posted→closing window overlaps, so trends appear retroactively from day one instead of waiting for snapshots to accumulate. Caveat to state honestly: weeks before the first crawl undercount, because postings that closed before tracking began were never captured.

## Email rendering rules (hard-won — do not relearn these by trial and error)

- Gmail **never renders HTML attachments** — it shows their source as text. Don't promise an HTML attachment will display.
- A full-dashboard PNG in the body displays but can't scroll/reflow — users reject it.
- The working design (already implemented in `build_email_body.py` + `daily_report.py`): the **email body is the dashboard**, rendered as email-safe HTML — tables + inline styles, hex colors only (no rgba/CSS-vars/grid), body kept well under Gmail's **102 KB clipping limit** (~42 KB typical). Only the trend line chart is an image, CID-embedded. Keep the plain-text fallback part.
- The `.html` dashboard file is still attached for full-size viewing after download; the workbook is attached for deep-dives.

## Modifying an existing pipeline

Data files + `.env` live in the workdir; scripts live here in the skill. Check the workdir's `*_daily_report.log` to diagnose failures (each step logs START/DONE/FAILED with output). Common issues: OneDrive file lock on an open Excel file (PermissionError on overwrite — ask user to close it), expired Gmail app password (535), API credit exhaustion (400 with "credit balance"), and a renamed agency in the mirror (0 matches — re-run discovery).
